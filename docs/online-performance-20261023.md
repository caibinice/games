# 联机延迟与流畅度优化（2026-10-23）

## 原因与改动

- 旧版 2P 直接显示约 20 Hz 的远端快照，自己的移动 / 跳跃 / 射击也要等“输入到房主，再返回快照”。新版本的魂斗罗 2P 先做本地预测，使用房主回传的输入序号、客户端时间戳和模拟时钟重放未确认操作，校正小误差时短时平滑；死亡、复活、拾取、伤害和过关始终以房主结果为准。
- 坦克 / 魂斗罗使用两个快照的插值，并限制短期外推；网络状态仍约 20 Hz，绘制按屏幕刷新率执行。连连看是离散棋盘操作，常规同步降至 10 Hz，成功连线立即请求下一帧，不添加预测伤害。
- 游戏逻辑从 requestAnimationFrame 拆开，独立 Worker 负责约 60 Hz 的唤醒，主线程保持共享模拟、输入、WebSocket，绘制只负责显示。房主页面绘制被降频时，不再把战斗时钟也拖成慢动作。暂停 / 离开会停止 Worker 定时器，恢复时不补算暂停时间；设备锁屏 / 系统挂起仍遵循断线暂停机制。
- 魂斗罗 2P 的调色图集只生成一次，移除每个绘制帧的 hue-rotate；效果初生时的动画索引加边界保护，避免插值时钟略早于效果出生时间导致渲染异常。
- 魂斗罗只发送渲染和本地预测所需状态，不发送刷怪表、AI 调度、随机状态等；动态实体数值保留两位小数。八关固定工况下快照主体体积减少约 22%～52%（完整网络包另含确认与声音元数据）。坦克地形编码按版本缓存，去掉重复 JSON 深拷贝。
- Socket 发送积压达到 24 KB 时跳过本次快照构建 / 发送，避免继续堆积；控制消息不采用这条快照阈值。手机方向只在状态变化时发布，消除重复的四方向消息。HUD 约 10 Hz 更新，不跟随游戏逐帧触发 Vue 渲染。
- 网络把按下 / 松开合并到同一模拟 tick 时，移动与动作保留一次短按；坦克的按键顺序列表也一起保留，避免网络抖动时短按直接丢失。
- 新快照带 netVersion=2；新客户端遇到旧房主时退回快照显示。声音仍保持字符串列表，以便旧客户端继续工作；新客户端过滤本地预测已播放的射击声，避免双重播放。

## 验证

- `tests/netcode.test.mjs`：八关相同 P2 物理、360 ms 模拟往返下预测 / 校正 / 松键、死亡 / 复活 / 房间切换、预测不修改共享结果、插值 / 外推边界、快照缩减、地形缓存失效、拥塞保护和 Worker 启停。
- `tests/browser/online-latency.mjs`：给 2P 输入和返回快照各增加 180 ms 延迟，测量实际绘制角色的首个移动，并检查房主逻辑时钟持续前进、松键后与权威位置收敛。一次同机对照为约 450 ms → 12 ms；这是本地视觉反馈，不是公网 RTT 降到 12 ms，也不是实体手机性能数据。
- 继续运行四游戏 PC / 模拟手机双端回归、共同暂停 / 恢复、断线重连、连连看冻结 / 补牌、匹配和原单机测试。
- 双方刷新后开新房即可完整启用；不改座舱后端、数据库、端口或 Nginx 路由。

实现参考：[浏览器后台绘制与计时器策略（MDN）](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)、[Valve Source SDK 的实体插值实现](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/client/interpolatedvar.h)。
